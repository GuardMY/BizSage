# BizSage 产品全版本里程碑

## 目的

本文档是 BizSage 的跨版本里程碑路线图。它定义当前 V1 MVP 之后的产品演进方向，同时确保实际开发范围仍由当前生效的版本里程碑文档控制。

当前生效的实施里程碑是 V1。后续版本在创建并批准各自详细里程碑文档之前，仅作为规划目标，不作为实施范围。

## 版本路线图

| 版本 | 主题 | 目标用户 | 核心结果 | 状态 |
| --- | --- | --- | --- | --- |
| V1 | 内部验证 MVP | 内部用户和运营人员 | 验证从数据到诊断的完整链路 | 进行中 |
| V2 | 封闭试点与运营强化 | 试点客户和运营人员 | 让诊断流程可用于受控客户场景 | 规划中 |
| V3 | 商业化就绪 | 付费企业用户、运营人员和管理员 | 增加商业化、报告、Android 和客户运营能力 | 规划中 |
| V4 | 规模化与生态 | 更大客户群和集成伙伴 | 提升规模、韧性、治理和外部集成能力 | 规划中 |

## V1 内部验证 MVP

详细计划：`docs/milestones/v1-mvp-milestones-zh-CN.md`。

### 范围

- 通过 mock 或可插拔适配器实现四类数据源采集。
- 实现数据治理、字段归一化、去重、固定信源权重、谣言过滤和敏感数据保护。
- 实现静态知识库、RAG 检索和带来源输出的诊断 Agent。
- 实现 Web 登录、会话、诊断聊天、来源查看和简单运营控制台。
- 实现本地单节点基础设施、运行手册和验收文档。

### 退出标准

- 四类数据源可以写入标准化记录。
- 诊断回答包含来源、时效说明、置信提示和免责声明。
- 无证据请求返回信息不足提示，而不是无依据结论。
- 手机号和身份类敏感字段按设计加密或脱敏。
- 完成 50 并发 API 请求和 4 小时单节点观察，或记录明确修复任务。

### 不在范围内

- Android 实现，除占位文档外不开发应用功能。
- 付费会员、权益计费和商业订单流程。
- PDF 报告。
- 多模型路由。
- 动态信源权重。
- 高可用、灾备和完整监控大盘。

## V2 封闭试点与运营强化

详细 V2 里程碑文档：尚未创建。

### 范围

- 将 V1 验证流程转化为面向选定客户场景的封闭试点流程。
- 扩展运营审核、通过、驳回和纠错流程。
- 强化信源质量控制、人工审计轨迹和证据生命周期管理。
- 增加可配置的行业和区域基线，但不引入动态模型路由。
- 增加用于产品和运营复盘的基础使用分析。
- 强化部署脚本、备份例程和故障恢复手册，支持单一类生产环境。

### 进入标准

- V1 退出标准已满足，或所有剩余失败项已有批准的修复任务。
- V1 API、数据库、部署和验收文档均已保持中英文同步。
- 试点客户场景和数据边界已记录。

### 退出标准

- 试点用户可以在运营支持下完成诊断和复核流程。
- 运营人员可以追踪情报变更的通过和驳回记录。
- 试点使用、失败和反馈数据可以导出复盘。
- 部署和备份手册支持可重复的封闭试点运行。

## V3 商业化就绪

详细 V3 里程碑文档：尚未创建。

### 范围

- 引入付费会员、权益校验、客户套餐和计费集成边界。
- 在诊断质量完成验证后，增加 PDF 或可分享报告生成。
- 如果 V2 封闭试点证据确认移动端需求，则实现 Android 应用流程。
- 增加面向客户的账号管理、组织管理和支持流程。
- 增强合规控制、保留策略和客户数据导出流程。
- 将可观测性从运行日志扩展为产品、服务和模型质量大盘。

### 进入标准

- V2 封闭试点验收完成。
- 商业定价、权益模型和合规假设已批准。
- 移动端范围基于真实用户需求验证，而不是占位假设。

### 退出标准

- 付费用户可以访问其权益范围内的诊断能力。
- 运营人员和管理员可以管理客户、套餐和支持流程。
- 报告生成具备来源可追溯和隐私控制。
- Android 范围已交付，或基于批准理由明确延期。

## V4 规模化与生态

详细 V4 里程碑文档：尚未创建。

### 范围

- 增加高可用、灾备、自动扩缩容和生产级监控。
- 只有当质量、成本或延迟需求可量化证明必要时，才引入多模型路由。
- 改进动态信源权重和基于反馈的排序。
- 增加第三方集成、伙伴 API 和受控数据交换。
- 支持更大客户群、多租户隔离强化和治理自动化。

### 进入标准

- V3 商业流程稳定。
- 生产使用已经体现明确的规模、集成或韧性需求。
- 可靠性、安全性和成本目标可度量。

### 退出标准

- 生产运行环境达到约定可用性和恢复目标。
- 外部集成通过有文档、有治理的 API 运行。
- 模型和信源排序变化可度量、可审计、可回滚。
- 平台运营可以扩展，常规事故不依赖人工干预。

## 跨版本规则

- 每个版本在开始实施前，必须先拥有自己的详细里程碑文档。
- V1 期间不得实施后续版本功能，除非同步更新 V1 里程碑文档并接受范围变更。
- 文档必须在同一次改动中维护英文和中文版本。
- 功能变更必须更新 `CHANGELOG.md` 和 `CHANGELOG-zh-CN.md`。
- 里程碑进度变更必须更新对应里程碑文档。
- Web、API、worker、collector、基础设施和 Android 模块必须保持目录隔离，并通过有文档的接口通信。
